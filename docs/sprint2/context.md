### 🛡️ 四、 面试防御话术（代码跑通后必背）

面试官看到“防超卖”，必定深挖，你需要准备好这三层防御：

**1. 追问：“为什么用 Lua 脚本，直接用 Redis 的 DECR 命令不行吗？”**
*   **答**：“直接用 `DECR` 的话，命令本身是原子的，但业务逻辑不是。如果库存已经为 0，`DECR` 会把它变成 -1。如果在 Java 代码里先 `GET` 再判断再 `DECR`，高并发下就会有竞态条件。Lua 脚本把‘判断’和‘扣减’打包在一起交给 Redis 执行，Redis 单线程处理保证了这个整体逻辑的原子性。”

**2. 追问：“如果 Redis 宕机了，你的库存扣减怎么办？”**
*   **答**：“目前在 Sprint 2 阶段只是单机 Redis。如果要在生产环境解决，一方面需要对 Redis 做主从+哨兵或 Cluster 保证高可用；另一方面，如果 Redis 真挂了，网关层必须做限流或熔断降级，直接拦截秒杀请求，绝对不能让请求穿透到 MySQL 数据库上去查库存，否则数据库会瞬间被打崩。”

**3. 追问：“Lua 里扣减成功了，但后面用户下单失败（比如没付款），库存怎么回滚？”**
*   **答**：“这是典型的最终一致性场景。当前 Sprint 2 我完成的是‘预扣减’环节，保证入口不超卖。后续完整的业务链路中，如果超时未支付，会通过定时任务扫表或者引入 Kafka 延迟消息，将 Redis 里的库存加回去（回滚）。至于分布式事务，考虑到 Nacos 3 和 Seata 的兼容性问题（可以顺带提一句 Spike 报告里的发现），项目规划后续会用‘本地消息表+定时补偿’来替代强一致性框架。”
